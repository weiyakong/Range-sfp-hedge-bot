# Extraction Tool — требования

Статус: рабочая спецификация. Требования будут уточняться по мере разбора исследовательских запросов.

## Назначение

Extraction tool — универсальный воспроизводимый инструмент для извлечения исследовательских выборок из итогового датасета.

Он должен **доставать и правильно совмещать данные**, но не делать исследовательские выводы, не подбирать пороги и не решать, какой рыночный сигнал является хорошим.

На старте **готовой child-leg hierarchy не предполагается**. Сначала tool должен уметь извлекать внутренние временные ряды внутри уже известных macro-legs. Правила child-leg segmentation будут исследоваться отдельно после корректного сбора данных.

---

## 1. Типы объектов исследования

Tool должен позволять запрашивать разные исследовательские объекты.

Первый обязательный тип:

### `parent_leg_window`

Взять конкретную известную macro-leg и вернуть всё движение внутри неё на выбранных меньших таймфреймах со всеми запрошенными признаками, **без заранее назначенных child legs**.

В дальнейшем должны поддерживаться и другие типы объектов, например:
- macro legs;
- snapshots внутри legs;
- transition events;
- окна до/после заданного события;
- после формализации child segmentation — child legs и parent/child relationships.

## 2. Фильтрация по структуре и контексту

Запрос должен поддерживать фильтры по доступной канонической разметке и метаданным, например:
- тип macro-leg;
- направление;
- выбранный parent;
- таймфрейм;
- период;
- положение наблюдения внутри parent по времени и/или цене;
- после появления child hierarchy — направление child относительно parent и другие parent/child filters.

Extraction tool не должен сам придумывать impulse/correction или child-leg boundaries. Он использует только уже утверждённую каноническую разметку либо возвращает сырые внутренние ряды для последующего исследования.

## 3. Выбор таймфреймов и feature windows

Запрос должен позволять:
- выбирать один или несколько таймфреймов одновременно;
- выбирать нужные feature windows;
- получать MTF-наборы внутри одного и того же parent/event window;
- явно фиксировать, какие TF/window комбинации вошли в выборку.

Пример задачи: взять одну 4H macro-leg и вернуть соответствующие 1H, 15m и 5m observations внутри её временных границ.

## 4. Point-in-time / as-of совмещение

Все predictor/context joins должны быть point-in-time correct.

Tool обязан:
- использовать только данные, которые были доступны к исследуемому моменту;
- учитывать `available_at_time` или эквивалентные поля доступности источников;
- исключать future leakage;
- сохранять информацию о времени доступности присоединённых данных.

Любой future outcome должен храниться отдельно от predictor features.

## 5. Извлечение траекторий признаков

Tool должен уметь возвращать не только одну строку/snapshot, но и динамику признаков по ходу объекта.

Нужно поддержать, например:
- полный временной ряд внутри parent-leg;
- выбранные точки по относительному времени;
- представление движения от 0 до 100% длительности parent;
- изменение feature values по ходу ноги.

Это необходимо для анализа фаз: начало → развитие → поздняя стадия → замедление → transition.

## 6. Детерминированные derived fields

Tool может рассчитывать только объективные, заранее определённые преобразования, необходимые для сопоставления выборок.

Допустимые примеры:
- доля времени внутри parent;
- доля ценового пути/амплитуды внутри parent;
- расстояние до parent high/low;
- направление observation относительно parent direction;
- нормализация по ATR/volatility;
- нормализация по parent amplitude;
- нормализация по parent duration;
- relative speed;
- relative efficiency;
- signed features, ориентированные по направлению parent/movement.

Derived fields должны быть детерминированными и документированными. Tool не должен превращать их в торговые правила.

## 7. Context joins

По запросу к основной выборке должны подключаться доступные контекстные данные, например:
- parent impulse / macro-leg metadata;
- Fib levels;
- FibTime context;
- structural levels;
- overlay levels;
- regime features других таймфреймов;
- spot/futures context, если он нужен конкретному исследованию;
- после появления канонической child hierarchy — child structure.

Каждый join должен быть явно указан в query specification и отражён в extraction report.

## 8. Outcome extraction

Tool должен уметь отдельно извлекать то, что произошло **после** исследуемого момента или события, чтобы затем оценивать прогностическую ценность features.

Примеры будущих outcome-полей:
- continuation parent direction;
- переход в range;
- continuation correction;
- завершение child-leg;
- завершение всей parent-correction;
- следующий structural event;
- время до события;
- последующее движение;
- MFE / MAE.

Критическое правило: future outcomes должны быть логически и физически отделены от predictor/context fields, доступных на момент решения.

## 9. Контроль качества данных

Tool должен уметь фильтровать и маркировать samples по качеству данных.

Необходимо:
- исключать samples с недопустимыми gaps по заданному правилу;
- при необходимости оставлять contaminated samples отдельной группой;
- показывать причины исключения;
- сохранять counts до и после каждого quality filter;
- не скрывать проблемные участки молча.

## 10. Полная воспроизводимость запроса

Для каждого extraction должны сохраняться:
- точный query/config;
- версии/идентификаторы использованных datasets;
- source hashes или эквивалентные идентификаторы версии;
- диапазон дат;
- filters;
- TF/window selections;
- selected features;
- joins;
- derived fields;
- outcome definition;
- quality rules;
- число samples до и после фильтров;
- причины exclusions;
- версия самого extraction tool.

Одинаковый запрос к одной версии данных должен давать одинаковую выборку.

## 11. Стандартные выходные артефакты

Минимальный набор результата одного extraction:

- `samples.parquet` — полная выборка;
- `samples.csv` — компактная/просматриваемая версия, когда размер позволяет;
- `query.json` — точная спецификация запроса;
- `extraction_report.json` — QA, source versions, counts, exclusions, joins и другие сведения о воспроизводимости.

При необходимости для trajectory-запросов может быть отдельный long-format parquet.

# Чего Extraction Tool делать не должен

Extraction tool **не должен**:
- искать лучшие thresholds;
- определять, какие признаки являются сильными или слабыми;
- оптимизировать RangeBot или ImpulseBot;
- самостоятельно объявлять рынок impulse/correction/range, если это не пришло из канонической разметки;
- придумывать child-leg hierarchy;
- доказывать или опровергать фрактальность;
- выполнять statistical significance testing как часть extraction;
- обучать модель;
- принимать торговые решения.

Разделение ответственности:

**Extraction layer:** корректно достать, совместить, нормализовать и задокументировать выборку.

**Analysis layer:** сравнивать группы, проверять гипотезы, искать повторяемость и делать исследовательские выводы.

---

# Критическое архитектурное правило

До появления проверенной child-leg segmentation основным объектом исследования внутренних движений является `parent_leg_window`: известная macro-leg + сырые/feature временные ряды меньших TF внутри её границ.

Child-leg hierarchy создаётся только после отдельного исследования правил segmentation и не должна быть предпосылкой для первой версии Extraction tool.
